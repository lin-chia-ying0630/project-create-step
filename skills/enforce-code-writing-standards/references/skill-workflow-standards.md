# Skill 與 Workflow 共用設計規範

## 責任分工

- `WORKFLOWS.md` 負責任務路由、授權轉換、共通禁止項目與跨 Skill 順序。
- `SKILL.md` 只負責一個可重複工作，描述何時使用、如何執行、何時停止及如何驗證。
- `references/` 保存只有特定情境才需要的細節；入口 Skill 必須直接連結並寫明讀取時機。
- `scripts/` 只承擔重複且要求確定性的操作，不把需要專業判斷的決策硬寫成關鍵字掃描。
- `agents/openai.yaml` 只保存介面 metadata、明確 invocation policy 及實際工具依賴，不重複 Skill 流程。

## Skill 契約

每個新增或重新設計的 Skill 依序確認：

1. **單一工作**：能以一個動詞描述，且不與現有 Skill 共用相同輸入、輸出及完成條件。
2. **觸發契約**：description 先寫核心能力，再寫使用情境；可能誤觸發時補上「不適用」邊界。
3. **前置條件**：列出必要檔案、授權、工具、外部系統及待確認決策。
4. **輸入契約**：說明從使用者、repository、正式文件或 runtime 取得哪些證據。
5. **執行步驟**：使用命令式、可排序步驟；判斷分支要有明確條件。
6. **輸出契約**：指定產物、欄位、位置或回報結構，不只寫「完成分析」。
7. **停止條件**：缺少授權、必要證據、安全前提或外部狀態時停止哪一段，不擴張權限。
8. **驗證契約**：分開定義成功、失敗、跳過與未執行，不以 build 代替行為驗證。

## 漸進揭露

- name 與 description 足以讓 agent 判斷是否選用，但不塞入完整流程。
- `SKILL.md` 保留每次執行都需要的核心步驟；領域 catalog、長範例與變體移入一層 references。
- 不建立 references 互相深層轉引；入口 Skill 應能直接指出任務需要讀取的檔案。
- 同一規則只保留一個權威來源，其他文件使用連結與責任摘要，不複製全文。

## 觸發與行為測試

新增或大幅調整 Skill 時至少準備三類測試提示：

| 類型 | 驗證目的 | 判定方式 |
|---|---|---|
| 正向觸發 | 典型任務會選到本 Skill | 輸入、輸出及主要步驟符合契約 |
| 不得觸發 | 相似字詞但責任不同 | 不選用本 Skill，或明確轉到正確入口 |
| 重疊觸發 | 同時符合兩個鄰近 Skill | 只選一個主要 Workflow，另一個作專項能力 |

測試應使用未洩漏預期答案的真實任務描述。只檢查 frontmatter、連結或 Markdown 格式不能證明 Skill 會被正確選用。

## 外部範例採用規則

網路上的 Skill、Workflow 或 prompt 只能作候選設計證據。採用前必須：

1. 確認來源、更新時間、授權與適用產品。
2. 拆出可重用的責任、輸入輸出、guardrail 與驗證方式。
3. 移除來源專案的工具、路徑、服務、帳號、業務代碼及完成宣告。
4. 與現有 Skills 比對；能補進既有規則時不新增 Skill。
5. 以本 repository 的正向、不得觸發與重疊案例驗證後才納入。

## Repository 探索與單一來源

本專案以 `skills/<skill-name>/` 作為可搬移治理來源。Codex repository 自動探索使用 `.agents/skills/`；需要自動探索時，以 symlink 指向治理來源，不複製內容。若執行環境不支援 symlink，搬移流程必須選定一個實際維護位置並更新文件，不得長期維護兩份可編輯副本。
