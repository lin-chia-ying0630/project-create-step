# 稽核與系統 Log 規範

## 共用原則

新增、修改、刪除、覆核狀態變更及敏感資料查詢必須依所屬模組記錄 append-only 稽核事件。實際表名、event type 與 business key 由已確認 schema／領域契約決定；共用規範不得指定某一功能的稽核表或狀態碼。

## 稽核事件最低欄位

- 事件唯一識別。
- 操作類型。
- 操作人員。
- requestId／traceId。
- 發生時間與明確時區。
- 所屬 feature 與經遮罩的業務鍵。
- 結果與錯誤碼。
- 必要時的變更摘要；不得保存不必要的完整敏感快照。

欄位名稱先沿用專案實際共用契約。只有兩個以上模組責任一致且 schema 可共用時才提取共用 audit component；單一業務事件與轉換規則留在 feature。

## 交易

- 正式異動與成功稽核在同一交易。
- 失敗嘗試或拒絕存取若必須在 rollback 後保存，才以獨立交易記錄。
- audit trail 為 append-only；更正以新事件補充，不更新或刪除舊事件。

## 系統 Log

| Level | 用途 |
|---|---|
| INFO | 啟停、完成的非敏感操作摘要 |
| WARN | 可恢復衝突、重試、棄用 API 使用 |
| ERROR | 未分類失敗與需要處理的外部依賴異常 |
| DEBUG | 僅非正式環境的診斷資訊，仍不得含敏感資料 |

每個請求應有 requestId，並在 response header 與 log context 保持一致。不得記錄 Authorization、token、密碼、完整身分證號、帳號、健康資料、SQL 參數、完整 request／response body 或憑證。

## 保存與查詢

保存期限由適用地區、資料分類與法遵核准來源決定；未取得正式來源不得自行填入固定年限。稽核查詢須授權、可追蹤且避免再次暴露敏感內容。

## 驗證

- 成功交易 commit 後可查到對應稽核事件。
- rollback 不留下假成功事件。
- 敏感查詢與拒絕存取依規格留下必要事件。
- 測試確認 append-only 限制及 log 遮罩。
